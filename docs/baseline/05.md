# Day 4 — Simulator Hardening, General Multi-Hop Forwarding, and Combined Failure Telemetry

## Objective

The goal of was to harden the simulation environment before moving into dynamic topology and adaptive routing.

The main priorities were:

```text
make packet identity safe
↓
make packet drops explainable
↓
generalize timed forwarding beyond one hardcoded relay
↓
integrate per-hop retries into simulated time
↓
combine congestion and unreliable-link behavior
↓
measure transmission effort correctly
```

B0 itself was not changed.

B0 remains the hop-count Dijkstra baseline.

---

# 1. Unique Packet IDs

Earlier multi-flow traffic generation used message IDs such as:

```text
MSG-0
MSG-1
MSG-2
```

for every source.

That meant different sources could generate duplicate IDs.

Example:

```text
A → MSG-0
C → MSG-0
E → MSG-0
```

This was unsafe because queue timing telemetry used packet identity when storing enqueue timestamps.

A duplicate ID could overwrite the timing information of another packet.

The traffic generator was updated so source identity becomes part of the packet ID.

Example:

```text
A → MSG-A-0
A → MSG-A-1

C → MSG-C-0
C → MSG-C-1
```

This guarantees unique IDs across simultaneous flows in the current deterministic simulator.

# 3. Explicit Packet Drop Reasons

Previously, timed packet results could record only:

```text
dropped = true
```

but not the reason for the drop.

A new drop-reason model was introduced.

Current reasons:

```text
QUEUE_FULL
RETRY_EXHAUSTED
TTL_EXPIRED
NO_ROUTE
LINK_UNAVAILABLE
```

This allows telemetry to distinguish different network failure mechanisms.

Example:

```text
Dropped = 6

QUEUE_FULL = 5
RETRY_EXHAUSTED = 1
TTL_EXPIRED = 0
NO_ROUTE = 0
LINK_UNAVAILABLE = 0
```

This is much more useful for research than a single aggregate drop count.

---

# 4. Timed Delivery Result Validation

The timed packet result was extended to include an optional `dropReason`.

Validation rules now enforce:

```text
Delivered packet
→ delivered = true
→ dropped = false
→ dropReason = null
```

and:

```text
Dropped packet
→ delivered = false
→ dropped = true
→ dropReason != null
```

This prevents inconsistent packet states.

A temporary test failure confirmed the validation was working correctly when a delivered packet was accidentally given a drop reason.

After correction, the timed end-to-end test again produced:

```text
===== TIMED END-TO-END TEST =====
Packet: MSG-001
Created at: 0
Delivered at: 7
End-to-end latency: 7
Delivered: true
=================================
```

# 6. General Timed Network Node

The earlier timed forwarding model was specialized around one relay.

A new `TimedNetworkNode` abstraction was introduced.

A timed network node wraps:

```text
node identity
queue
service time
packet processing callback
queue telemetry
```

This makes the service-node behavior reusable for arbitrary network nodes.

Validation output:

```text
===== TIMED NETWORK NODE =====
Node processed: B
Completion time: 5
Processed packets: 1
==============================
```

# 7. General Multi-Hop Timed Network Simulator

The simulation was generalized from a special:

```text
A → B → D
```

model into arbitrary path forwarding.

Example path:

```text
A → B → C → D
```

Each intermediate node can independently have:

```text
queue capacity
service time
packet-processing delay
```

The simulator now progresses node by node through the configured route.

Test configuration:

```text
A → B link delay = 1
B service = 3
B → C link delay = 1
C service = 4
C → D link delay = 1
D service = 1
```

Observed result:

```text
===== GENERAL TIMED NETWORK =====
Path: [A, B, C, D]
Delivered: true
Delivered at: 11
End-to-end latency: 11
B processed: 1
C processed: 1
D processed: 1
=================================
```

This was a major structural improvement because the timed simulator is no longer tied to one hardcoded relay.

---

# 8. Timed Link Result

A timed link result model was added.

It records:

```text
success
attempts
totalDelay
retransmissions
```

Example:

```text
success = true
attempts = 2
totalDelay = 4
retransmissions = 1
```

This means:

```text
attempt 1 failed
attempt 2 succeeded
```

and two physical attempts consumed four simulated time units.

---

# 9. Deterministic Timed Link Transmitter

A generic timed link transmitter interface was introduced.

A deterministic implementation allows exact control over link behavior.

This is important for reproducible experiments.

Example test behavior:

```text
B → C

attempt 1 = fail
attempt 2 = success
```

Observed result:

```text
===== TIMED LINK RETRY TEST =====
Success: true
Attempts: 2
Retransmissions: 1
Total link delay: 4
=================================
```

This confirmed that retry behavior can be modeled as deterministic simulated time.

---

# 10. Retry-Aware General Multi-Hop Simulation

The general timed network simulator was then upgraded to use the new timed link transmitter.

The old fixed link-delay model was removed.

Each hop now asks the link transmitter for:

```text
success / failure
attempt count
total link delay
```

Normal all-success forwarding remained unchanged.

Observed result:

```text
===== GENERAL TIMED NETWORK =====
Path: [A, B, C, D]
Delivered: true
Delivered at: 11
End-to-end latency: 11
B processed: 1
C processed: 1
D processed: 1
=================================
```

This confirmed that the retry-aware upgrade did not break normal forwarding behavior.

# 11. Retry Delay Contributes to End-to-End Latency

The next experiment forced one failed attempt on the middle hop.

Path:

```text
A → B → C → D
```

Link behavior:

```text
B → C
attempt 1 = fail
attempt 2 = success
```

Observed result:

```text
===== TIMED NETWORK RETRY PATH =====
Path: [A, B, C, D]
B -> C: first attempt fails, second succeeds
Delivered: true
Delivered at: 12
End-to-end latency: 12
====================================
```

Normal latency:

```text
11
```

Retry-path latency:

```text
12
```

Therefore, the additional retry delay correctly contributes to full end-to-end latency.

---

# 12. Retry Exhaustion

A controlled case forced every attempt on `B → C` to fail.

The simulator correctly stopped the packet after the retry budget was exhausted and recorded:

```text
RETRY_EXHAUSTED
```

C and D did not process the packet.

This establishes a clear distinction between temporary link failure and persistent failure beyond the retry budget.

# 14. Combined-Failure Interpretation

Packet accounting is internally consistent:

```text
Delivered + Dropped
= 4 + 6
= 10 generated
```

Drop accounting is also consistent:

```text
QUEUE_FULL + RETRY_EXHAUSTED
= 5 + 1
= 6 total drops
```

This means the simulator can now observe and separate:

```text
congestion-related failure
+
wireless retry-related failure
```

inside the same end-to-end multi-hop experiment.

# 18. Research Significance

Day 4 did not attempt to prove that a future adaptive protocol is better than B0.

The main contribution of the day was to create a more defensible experimental platform.

The simulator now exposes:

```text
queue pressure
queue delay
queue overflow
retry behavior
retry exhaustion
end-to-end latency
destination PDR
transmission effort
drop causes
```

These are candidate measurements that can later support dynamic multi-metric routing and confidence assessment.

---

# 19. Current Limitations

Several limitations remain:

1. Dynamic topology is not yet integrated into active traffic.
2. Routes are still supplied to the timed simulator as fixed paths.
3. Link behavior is deterministic.
4. Simulated time remains abstract and is not yet mapped to milliseconds or seconds.
5. Real BLE behavior has not yet been integrated.
6. Source-side processing remains simplified.

These limitations are acceptable for the current baseline-hardening stage.

# Day 4 Final Summary

Day 4 transformed the timed simulator from a mostly single-relay congestion model into a general multi-hop, failure-aware simulation environment.

Before:

```text
special relay forwarding
+
queue congestion
+
separate retry tests
```

After:

```text
general multi-hop path
        ↓
per-node queues
        ↓
per-node service time
        ↓
per-hop timed transmissions
        ↓
retry behavior
        ↓
retry exhaustion
        ↓
explicit drop causes
        ↓
destination delivery
        ↓
latency + queue + transmission telemetry
```

The final combined experiment produced:

```text
10 generated
4 delivered
6 dropped

5 queue-full drops
1 retry-exhausted drop

40% PDR

19 average latency
19.5 median latency
26 maximum latency

19 logical hop attempts
22 physical transmission attempts
4 failed attempts
3 retransmissions
```

therefore established a stronger simulation foundation for the next stage: dynamic topology, mobility-style failures, network partitions, and route recovery during active traffic.
