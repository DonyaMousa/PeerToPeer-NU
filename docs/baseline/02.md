# 02 — B0 Packet Forwarding + Reliability Baseline

## Goal

The goal of 02 was to extend the B0 baseline from a routing-only implementation into a packet-level network simulation.

At the end of 01, B0 could:

- represent nodes and edges as a graph;
- calculate shortest paths using Dijkstra;
- build and query routing information;
- cache calculated routes;
- invalidate routes when topology changed;
- measure routing calculations and cache behavior.

However, B0 could only determine a route such as:

```text
A → B → D
```

It did not yet simulate an actual packet travelling through that route.

Day 2 therefore introduced:

- packets;
- packet forwarding state;
- bounded node queues;
- simulated network nodes;
- hop-by-hop forwarding;
- link transmission;
- bounded retransmissions;
- packet drops;
- aggregate network telemetry;
- packet reliability experiments.

B0 remains the normal hop-count Dijkstra baseline.

Every graph edge has:

```text
weight = 1
```

Therefore, B0 selects routes based only on the number of hops.

---

# 1. Packet Model

A `Packet` model was introduced to represent the data being transported through the network.

Each packet contains:

```text
messageId
sourceId
destinationId
createdAt
ttl
payload
```

Example:

```text
messageId      = MSG-001
sourceId       = A
destinationId  = D
createdAt      = 1000
ttl            = 5
payload        = "Hello D"
```

The `messageId` uniquely identifies the packet.

This will later support mechanisms such as duplicate detection and duplicate suppression.

The source and destination identify the endpoints of the communication.

`createdAt` provides the foundation for future end-to-end latency measurements.

TTL limits how far a packet may travel.

For example:

```text
Initial:

A
TTL = 5
Hop count = 0

A → B

TTL = 4
Hop count = 1

B → D

TTL = 3
Hop count = 2
```

This prevents packets from being forwarded indefinitely.

---

# 2. Packet State

The original packet represents the message itself.

A separate `PacketState` was introduced to represent what is currently happening to the packet.

It tracks:

```text
currentNodeId
remainingTtl
hopCount
delivered
dropped
```

This creates a separation between:

```text
Packet
=
what the message is
```

and:

```text
PacketState
=
what is happening to the packet during forwarding
```

For example:

```text
Packet starts at A

currentNode = A
TTL = 5
hopCount = 0
```

After:

```text
A → B
```

the state becomes:

```text
currentNode = B
TTL = 4
hopCount = 1
```

After:

```text
B → D
```

the state becomes:

```text
currentNode = D
TTL = 3
hopCount = 2
delivered = true
```

---

# 3. Integration with B0 Hop-Count Dijkstra

The packet model was then connected to the existing B0 routing implementation.

A controlled topology was used:

```text
A → B → D
```

and:

```text
A → C → E → D
```

Because every edge had weight `1`, the route costs were:

```text
A → B → D
Cost = 2
```

and:

```text
A → C → E → D
Cost = 3
```

B0 correctly selected:

```text
A → B → D
```

A packet was then forwarded through this selected route.

Observed result:

```text
===== B0 PACKET ROUTING TEST =====

Selected route: [A, B, D]
Route cost: 2
Packet ID: MSG-B0-001
Final node: D
Hop count: 2
Remaining TTL: 3
Delivered: true

==================================
```

This demonstrated that the routing output could be consumed by the packet-forwarding layer.

---

# 4. Bounded Packet Queues

A bounded FIFO packet queue was introduced for simulated nodes.

FIFO means:

```text
First In
First Out
```

For example:

```text
MSG-1 enters
MSG-2 enters
MSG-3 enters
```

They are normally processed as:

```text
MSG-1
MSG-2
MSG-3
```

The queue also has a maximum capacity.

Example:

```text
Queue capacity = 2

MSG-1 → accepted
MSG-2 → accepted
MSG-3 → rejected
```

This provides the foundation for later congestion experiments.

If many routes share the same relay, packets may eventually arrive faster than the relay can process them.

That can produce:

```text
queue buildup
      ↓
queue waiting time
      ↓
queue overflow
      ↓
packet drops
```

The queue itself has been implemented and tested.

However, realistic congestion has not yet been measured because the current simulator still processes packet forwarding synchronously.

---

# 5. Simulated Nodes

The original `Node` class continues to represent a node inside the routing graph.

A separate `SimulatedNode` was introduced to represent a node participating in packet forwarding.

Conceptually:

```text
Node
=
routing identity
```

while:

```text
SimulatedNode
=
node identity
+
packet queue
+
packet receive/process behavior
```

This keeps routing topology separate from runtime simulation behavior.

A simulated node can:

- receive a packet;
- place a packet into its queue;
- process the next packet;
- report queue occupancy;
- reject packets when its queue is full.

---

# 6. B0 Forwarding Simulator

A `B0ForwardingSimulator` was introduced to automate packet forwarding.

Previously, tests manually moved a packet between nodes.

The forwarding simulator now performs the process itself:

```text
Packet
   ↓
Source
   ↓
Source Queue
   ↓
B0 Routing Table
   ↓
Selected Route
   ↓
Next Hop
   ↓
Relay Queue
   ↓
Next Hop
   ↓
Destination
```

For:

```text
A → B → D
```

the simulator performs:

```text
Packet enters A queue
        ↓
A processes packet
        ↓
A → B
        ↓
B receives packet
        ↓
Packet enters B queue
        ↓
B processes packet
        ↓
B → D
        ↓
Delivered
```

The initial forwarding result was:

```text
===== B0 FORWARDING SIMULATOR =====

Packet: MSG-SIM-001
Visited: [A, B, D]
Transmissions: 2
Hop count: 2
Remaining TTL: 3
Delivered: true
Dropped: false

===================================
```

This demonstrated successful automatic hop-by-hop forwarding using the B0 route.

---

# 7. Link Transmission Abstraction

Initially, every simulated link always succeeded.

This was unrealistic because wireless links may fail because of:

- interference;
- mobility;
- temporary disconnection;
- weak or unstable links;
- radio conditions.

A `LinkTransmitter` abstraction was therefore introduced.

The forwarding simulator now asks the link-transmission layer whether a physical transmission succeeds.

Conceptually:

```text
B0 Forwarding Simulator
          ↓
     LinkTransmitter
          ↓
Did A → B succeed?
```

This separation allows different link models to be used later.

For example:

```text
perfect simulated link
probabilistic lossy link
trace-based link
real Bluetooth transport
```

without rewriting B0 itself.

---

# 8. Bounded Retry Behavior

A `RetryLinkTransmitter` was introduced.

A hop may now require multiple physical transmission attempts.

Example:

```text
A → B

Attempt 1 ❌
Attempt 2 ✅
```

The hop eventually succeeds.

Another example:

```text
A → B

Attempt 1 ❌
Attempt 2 ❌
Attempt 3 ❌
```

The retry budget is exhausted and the packet forwarding attempt fails.

Retries are bounded so the network cannot continuously retransmit the same packet forever.

---

# 9. ACK Abstraction

At the current simulation stage, an explicit ACK packet is not transmitted separately.

Instead:

```text
successful transmission
=
successful delivery/ACK evidence for that hop
```

Therefore:

```text
success
→ stop retrying
```

while:

```text
failure
→ retry if retry budget remains
```

A more detailed ACK model can be introduced later if required.

---

# 10. Successful Retry Test

The first retry integration test used:

```text
A → B → D
```

The controlled transmission behavior was:

```text
A → B

Attempt 1 ❌
Attempt 2 ✅
```

followed by:

```text
B → D

Attempt 1 ✅
```

Observed result:

```text
===== B0 RETRY FORWARDING =====

Visited: [A, B, D]
Successful hops: 2
Transmission attempts: 3
Retransmissions: 1
Delivered: true
Dropped: false

===============================
```

This demonstrated that a two-hop route does not necessarily require only two physical transmission attempts.

The route contained:

```text
2 logical hops
```

but required:

```text
3 physical transmission attempts
```

because one link required retransmission.

---

# 11. Retry Exhaustion

The opposite case was also tested.

For:

```text
A → B
```

all allowed transmission attempts were configured to fail:

```text
Attempt 1 ❌
Attempt 2 ❌
Attempt 3 ❌
```

The retry budget was exhausted.

The packet forwarding attempt was therefore marked as:

```text
Delivered = false
Dropped = true
```

This establishes bounded failure behavior.

A dropped packet means that the current packet-forwarding attempt failed.

It does not necessarily mean that a future application-level message system must permanently delete the user's original message.

Message persistence and later store-carry-forward behavior belong to a higher layer that will be introduced later.

---

# 12. Correct Transmission Telemetry

The telemetry was refined to distinguish several different concepts.

These are now measured separately:

```text
attemptedHops
successfulHops
transmissionAttempts
successfulTransmissionAttempts
failedTransmissionAttempts
initialTransmissionAttempts
retransmissions
```

This distinction is important.

Consider:

```text
A → B

Attempt 1 ❌
Attempt 2 ❌
Attempt 3 ✅
```

This represents:

```text
Attempted hops = 1
Successful hops = 1

Transmission attempts = 3
Initial attempts = 1
Retransmissions = 2

Successful transmission attempts = 1
Failed transmission attempts = 2
```

A failed transmission attempt is not automatically the same thing as a retransmission.

For example:

```text
Attempt 1 ❌
Attempt 2 ❌
Attempt 3 ❌
```

contains:

```text
3 failed transmission attempts
```

but only:

```text
2 retransmissions
```

because the first transmission was the initial attempt.

This distinction was corrected before continuing with larger experiments.

---

# 13. Network Telemetry

A `NetworkTelemetry` collector was introduced to aggregate results from multiple packets.

It records:

```text
generated packets
delivered packets
dropped packets

attempted hops
successful hops

transmission attempts
successful transmission attempts
failed transmission attempts
initial transmission attempts
retransmissions
```

It also calculates metrics such as:

## Packet Delivery Ratio

```text
PDR =
delivered packets / generated packets
```

## Drop Rate

```text
Drop Rate =
dropped packets / generated packets
```

## Transmission Attempts per Delivered Packet

```text
Attempts per delivered packet =
total transmission attempts / delivered packets
```

These metrics allow B0 to be evaluated over workloads instead of examining only one packet at a time.

# 14. Experiment B0-E002

## Packet Reliability Under an Unreliable Shortest Path

### Research Question

How does B0 hop-count routing behave when its minimum-hop route contains an unreliable link?

---

## Experimental Topology

Two routes were available between A and D.

Shortest route:

```text
A → B → D
```

Cost:

```text
2 hops
```

Alternative route:

```text
A → C → E → D
```

Cost:

```text
3 hops
```

Because B0 uses hop count only, it selected:

```text
A → B → D
```

The three-hop alternative remained available but was not selected.

---

## Experimental Conditions

A total of:

```text
100 packets
```

were generated from A to D.

The `A → B` link followed a deterministic reliability pattern.

### 70 packets

The first transmission succeeded:

```text
Attempt 1 ✅
```

### 20 packets

The first transmission failed and the second succeeded:

```text
Attempt 1 ❌
Attempt 2 ✅
```

### 10 packets

All three allowed transmission attempts failed:

```text
Attempt 1 ❌
Attempt 2 ❌
Attempt 3 ❌
```

These packets were dropped.

The:

```text
B → D
```

link was configured to succeed.

The maximum number of transmission attempts per hop was:

```text
3
```

The experiment was deterministic so the result could be reproduced exactly.

---

# 15. B0-E002 Result

The corrected experiment produced:

```text
===== B0 PACKET RELIABILITY EXPERIMENT =====

Generated packets: 100
Delivered packets: 90
Dropped packets: 10

PDR: 90.0%
Drop rate: 10.0%

Attempted hops: 190
Successful hops: 180

Transmission attempts: 230
Successful transmission attempts: 180
Failed transmission attempts: 50
Initial transmission attempts: 190
Retransmissions: 40

Attempts per delivered packet:
2.5555555555555554

ROUTING CACHE

Route requests: 100
Cache hits: 99
Cache misses: 1
Dijkstra calculations: 1

============================================
```

---

# 16. Packet Delivery Result

Out of 100 generated packets:

```text
90 were delivered
10 were dropped
```

Therefore:

```text
PDR =
90 / 100
=
90%
```

and:

```text
Drop Rate =
10 / 100
=
10%
```

The 10 dropped packets exhausted the allowed transmission attempts on the unreliable `A → B` link.

---

# 17. Hop Measurements

The experiment recorded:

```text
Attempted hops: 190
Successful hops: 180
```

The 90 successfully delivered packets each completed two hops:

```text
90 × 2
=
180 successful hops
```

The 10 failed packets attempted the first hop:

```text
A → B
```

but never completed it.

Therefore:

```text
180 successful route hops
+
10 failed attempted hops
=
190 attempted hops
```

---

# 18. Physical Transmission Measurements

The network performed:

```text
230 total physical transmission attempts
```

Of these:

```text
180 were successful
50 failed
```

Therefore:

```text
230 - 180
=
50 failed transmission attempts
```

---

# 19. Retransmission Measurement

Every attempted hop has one initial transmission attempt.

The experiment contained:

```text
190 attempted hops
```

Therefore there were:

```text
190 initial transmission attempts
```

The total number of physical attempts was:

```text
230
```

Therefore:

```text
Retransmissions
=
230 - 190
=
40
```

The final distinction is:

```text
Failed transmission attempts = 50
Retransmissions              = 40
```

These metrics represent different properties and should not be treated as equivalent.

---

# 20. Transmission Cost per Delivered Packet

The experiment required:

```text
230 physical transmission attempts
```

to successfully deliver:

```text
90 packets
```

Therefore:

```text
230 / 90
=
2.555555...
```

or approximately:

```text
2.56 transmission attempts per delivered packet
```

Under perfect conditions, the selected two-hop route would require:

```text
2.0 transmission attempts per delivered packet
```

The unreliable-link scenario therefore required additional transmission work.

This does not by itself measure battery consumption, but transmission attempts can later be used as one component of communication-overhead and energy-related evaluation.

---

# 21. Routing Cache Result

The topology did not change during the experiment.

The routing telemetry reported:

```text
Route requests: 100
Cache hits: 99
Cache misses: 1
Dijkstra calculations: 1
```

The first packet required a Dijkstra calculation.

The resulting route:

```text
A → B → D
```

was cached.

The remaining 99 packets reused the cached route.

This demonstrates that B0 avoids recalculating Dijkstra for every packet when the topology remains unchanged.

---

# 22. Main Observation

The experiment reveals an important distinction between computational routing efficiency and forwarding behavior.

## Routing Computation

B0 was computationally efficient:

```text
100 route requests
99 cache hits
1 cache miss
1 Dijkstra calculation
```

The route did not need to be repeatedly recalculated.

## Packet Forwarding

However, the cached route contained an unreliable link.

Because B0's routing cost only represented hop count, the route remained:

```text
A → B → D
```

despite the simulated failures on `A → B`.

The resulting packet-level measurements were:

```text
PDR:                    90%
Drop rate:              10%

Transmission attempts: 230
Failed attempts:         50
Retransmissions:         40

Attempts per delivery:  2.56
```

Therefore, efficient route computation and caching do not automatically guarantee efficient or reliable wireless forwarding.

---

# 23. What This Experiment Does NOT Prove

This experiment does not prove that DynaBLE-RX is superior to B0.

It also does not represent real Android Bluetooth performance yet.

The link behavior was deliberately controlled and deterministic.

The experiment establishes a reproducible baseline showing how the current hop-count protocol behaves when its selected shortest path contains an unreliable link.

Future protocols must be tested under the same or equivalent conditions before comparisons can be made.

---

# 24. Why This Baseline Matters

The experiment provides measurable quantities that can later be compared with the proposed protocol.

Future comparisons can examine whether another routing strategy changes:

```text
Packet Delivery Ratio
Drop Rate
Transmission Attempts
Retransmissions
Failed Transmission Attempts
Attempts per Delivered Packet
Hop Count
```

For example, a future multi-metric protocol might decide that:

```text
A → B → D
```

is short but unreliable and instead select:

```text
A → C → E → D
```

if the longer route produces a better overall cost.

That behavior has not been implemented or evaluated yet.

The current experiment exists specifically to establish B0 before introducing such mechanisms.

---

# 25. Current Simulation Limitation

The simulator currently processes forwarding synchronously.

Conceptually:

```text
Packet 1
→ processed

Packet 2
→ processed

Packet 3
→ processed
```

Because of this, the packet queue implementation exists and has been tested, but realistic congestion has not yet been measured.

Real queue buildup requires packets to arrive while other packets are still waiting or being transmitted.

Therefore the next simulation stage requires a time or event model.

---

# 26. Next Experimental Stage

The next stage will introduce:

```text
Simulated Time
      ↓
Traffic Generation
      ↓
Packet Arrival Rate
      ↓
Node Processing / Transmission Rate
      ↓
Multiple Packets and Flows
      ↓
Shared Relays
      ↓
Queue Buildup
      ↓
Queue Waiting Time
      ↓
Queue Overflow
      ↓
Congestion-Related Drops
```

This will allow B0 to be evaluated under traffic load rather than only under link unreliability.

A particularly important scenario will involve multiple flows sharing the same minimum-hop relay.

For example:

```text
A ─┐
C ─┼→ B → D
E ─┘
```

If B0 repeatedly selects B because it belongs to the shortest routes, traffic may accumulate at B.

The future experiments will measure this behavior rather than assuming it occurs.
